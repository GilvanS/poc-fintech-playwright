# Onboarding: CT03.7 — Reenvio do pagamento cai na guarda de idempotência

> Doc para novos mantenedores da suíte E2E (`poc-fintech-playwright`).
> Explica **o que** o CT03.7 prova, **por que** ele existe e **como** o fluxo de
> injeção + reenvio funciona por baixo dos panos.

---

## 1. O que é

`@CT03.7` é um cenário BDD permanente (`tests/features/faturas.feature`) que valida a
**guarda de idempotência** do pagamento de fatura do FintechBankApp:

> Um pagamento de **mesmo CPF + mesmo valor** dentro de uma janela de **90 segundos**
> é tratado como reenvio. A API o **descarta sem débito** (nenhuma transação no banco)
> e responde de forma inequívoca. A UI mostra um **aviso informativo** — nunca um
> "sucesso" fingindo débito.

Rode com:

```bash
npm run test:ct03.7        # cenário isolado (bdd:gen + playwright --grep "@CT03.7")
npm run test:ct03.all      # família CT03 inteira (CT03.1–05 + CT03.7)
```

Duração típica: **45–60s**.

---

## 2. Por que ele existe (a história em 1 minuto)

O bug CT03.2 (2026-09) tinha dois sintomas que enganavam todo mundo:

1. A API **descartava** o reenvio (proteção contra dupla cobrança funcionava), **mas**
   respondia `success: true, amountPaid: <valor>` — como se tivesse debitado agora.
2. A WEB, recebendo esse "sucesso", exibia o modal **"Pagamento realizado com sucesso!"**
   com o valor — o famoso **sucesso falso**.
3. Pior: a suíte E2E passava, porque só olhava a UI. **2 de 8 execuções** rodaram sem
   débito nenhum e ninguém soube.

A correção (PR #80 no FintechBankApp, squash `548c9153`) mudou o contrato dos dois lados:

| Camada | Antes | Depois |
|---|---|---|
| **API** | Descartava mas respondia `amountPaid: valor` | Resposta inequívoca: `idempotent: true, debitado: false, amountPaid: 0, paymentId, originalPaymentDate` |
| **WEB** | Modal falso de sucesso | Toast informativo: *"Este pagamento já havia sido processado (data) — nenhum novo valor foi debitado. Confira o extrato para conferir o lançamento."* |
| **Suíte** | Passava fingindo débito | Assert explícito: a dívida derivada (`closedInvoiceResidual`) **tem que cair exatamente o valor pago**, senão falha com causa |

Documentação completa: [`docs/BUG-REPORT-FATURA-FECHADA-IMUTAVEL-PAGAMENTO-MINIMO.md`](BUG-REPORT-FATURA-FECHADA-IMUTAVEL-PAGAMENTO-MINIMO.md).

O CT03.7 **automatiza a prova** dessa correção de ponta a ponta, para sempre — antes dele
isso era validado com um script one-off (removido) rodado à mão.

---

## 3. O fluxo (o coração do cenário)

### 3.1 O problema do timing que o cenário resolve

A guarda olha os **últimos 90s**. Mas o intervalo natural entre dois cliques de
confirmação na suíte fica em **~100–116s** (run completa + reinício do navegador) —
**fora da janela**. Ou seja: rodar o cenário de pagamento duas vezes nunca dispararia
a guarda por si só.

A solução: **injetar o "pagamento original" via API com o modal de PIN já aberto na UI**.
Assim o reenvio pela UI chega **2–10s** depois do POST da API — dentro da janela com
folga, de forma **determinística** (sem sleep, sem corrida).

### 3.2 Sequência passo a passo

```
 ┌──────────────────────────────────────────────────────────────────────┐
 │ Background: login pela UI (CPF/SENHA da linha CT03.7 de TBL_CENARIOS)│
 └──────────────────────────────────────────────────────────────────────┘
 1. Steps comuns do CT03.2 (reaproveitados, nenhum código duplicado):
    Dashboard → Faturas → tab "Fatura Fechada" → "Pagar Fatura" →
    preset "Pagar Mínimo (10%)" → "Continuar" → modal de PIN ABERTO.
    O modal exibe "confirmar o pagamento de R$ X" — X = 10% do TOTAL
    imutável da fechada, truncado em 4 casas (mesma regra do app).

 2. STEP NOVO — "eu injeto o pagamento original via API com o modal de PIN aberto"
    ├── Lê o estado real pela API: closedInvoiceResidual + paymentHistory.length
    ├── POST /api/cards/invoice/pay (mesmo cpf + pin + amount = mínimo)
    │   → DÉBITO REAL nº 1 (transação INVOICE_PAYMENT no banco)
    │   → a janela de 90s da guarda ABRE AQUI
    └── Prova da injeção: residual caiu o valor injetado E histórico +1.
        Se não, falha cedo com "[Injeção incoerente]".

 3. STEP NOVO — "eu digito o PIN da massa para o reenvio do pagamento"
    PIN digitado dígito a dígito → POST do reenvio chega 2–10s depois do
    da injeção → CAI NA GUARDA (mesmo cpf+valor, <90s).
    A API NÃO debita, NÃO grava transação, responde idempotent.

 4. STEP NOVO — "devo ver o aviso de pagamento já processado sem débito novo"
    ├── Toast VISÍVEL: role=alert + testid toast-info,
    │   título "Pagamento já processado", mensagem "...já havia sido processado..."
    └── Modal "Pagamento realizado com sucesso!" NUNCA visível (toBeHidden).
    ⚠️ Roda IMEDIATAMENTE após o PIN: o toast some em ~8s.

 5. STEP NOVO — "o histórico de pagamentos cresce exatamente 1 desde a captura inicial"
    ├── Consulta a API de novo: paymentHistory = antes + 1 (só a injeção).
    │   Se cresceu 2+ → "[Débito duplicado] ... a guarda NÃO funcionou".
    └── Residual estável = dividaPosInjecao (o reenvio não mexeu em nada).
```

### 3.3 Contrato da resposta `idempotent` (o que a API devolve)

```jsonc
{
  "success": true,
  "idempotent": true,
  "debitado": false,
  "amountPaid": 0,
  "paymentId": "714bdd49-…",        // id do pagamento ORIGINAL (o que debitou)
  "originalPaymentDate": "2026-09-26T12:11:29…",
  "user": { … }                      // estado atualizado do usuário
}
```

Se um dia o payload voltar a trazer `amountPaid > 0` sem débito, **a regressão do bug
original voltou** — o passo 4 falha (modal falso reaparece).

## 5. Massa de dados: como o CT03.7 consome (e cansa) a linha

- A linha `CT03.7` é **cópia dos dados da linha CT03.2** (mesmo CPF/SENHA/PIN) — o
  cenário é autocontido (injeção + reenvio em segundos), então não precisa de conta nova.
- **Cada execução debita um mínimo REAL** (é a injeção). O residual derivado
  (`closedInvoiceResidual`) diminui a cada run; a coluna `fat_fechada` da planilha fica
  no valor original mesmo (o card da fatura fechada é imutável por regra de negócio —
  por isso o cenário lê os valores reais via API, nunca a planilha, para as asserções).
- Quando o residual cair **abaixo do mínimo** (10% do total), a **injeção falha**
  (`[Injeção incoerente]` ou recusa da API) → hora de trocar a massa: atualize a linha
  CT03.7 em `TBL_CENARIOS` com um CPF do pool (`tbl_de_massas.csv` / gerador de massa)
  que tenha fatura fechada com residual folgado.
- **Fonte do schema da massa:** as colunas estendidas do pool (`tbl_pf_*`, `tbl_pa_*`,
  `tbl_reneg`, `tbl_cemiterio_teste`…) vêm dos modelos de cálculo
  **`data/CALCULO DE PF_RENEG_V1.xlsm`** e **`data/CALCULO DE PF_RENEG_V1_PA.xlsm`**
  (abas IOF 1/2, PF, PA, SC, PE-TR-CRE — versionados no commit `ab9a7d4`). Ao regenerar
  massa ou interpretar esses campos, esses arquivos são a fonte de verdade do negócio
  (ver também `docs/plan-geração-massa-5.0.md`).
- Para gravar na planilha: **sempre** via `tests/utils/excelTableAppender.ts`
  (append-only, preserva a formatação de Tabela) ou edição XML cirúrgica — **nunca**
  `XLSX.writeFile()`. E **feche o Excel antes** (o arquivo fica travado e a escrita
  falha com EPERM).

## 6. Armadilhas conhecidas (e o que cada falha significa)

| Sintoma | Causa provável | O que fazer |
|---|---|---|
| `[Injeção do pagamento original via API falhou... idempotent]` | Rodou `test:ct03.2` **menos de 90s antes** — mesmo CPF+valor, a injeção caiu na guarda | Espere ≥90s e rode de novo (ver nota no README) |
| `[Débito duplicado] Histórico de pagamentos: N → N+2` | **Regressão no app**: a guarda não descartou o reenvio | Inspecione `transactions INVOICE_PAYMENT` no banco e o stdout da API (`[pay][idempotencia]`); acione o time do FintechBankApp |
| Toast não visível / timeout no passo 4 | Markup do Toast mudou no WEB (locators: role=alert + `toast-info`/`toast-message`) ou alguém reintroduziu o modal falso | Confira `WEB/components/Toast.tsx` e `InvoicesAllureView.tsx` no checkout do app |
| `[Injeção incoerente]` | Massa sem residual suficiente, ou API em estado estranho | Veja o residual no log da injeção; troque a massa se cansada |
| Flake no Background (página não sai da Landing, "Ocultar Menu" não aparece) | Timing transitório de login — **visto 1×** em dezenas de runs | Reexecutar; se persistir, investigar `LandingPage`/login |
| Bottom sheet verde (`InvoiceSummarySheet`) intercepta cliques ao abrir Faturas | Quirk da UI conhecido | Os métodos do `FaturasPage` já lidam; se aparecer novo padrão, trate na Page, não no step |

## 7. Regras que o cenário NÃO pode quebrar

1. **Sem fallback silencioso** — qualquer dado ausente (residual, CPF, contagem) falha
   com mensagem explícita dizendo qual step rodar antes. Nunca "assumir" valor.
2. **A injeção é débito legítimo** — não é mock, não é seed. É um pagamento real que o
   banco registra. É isso que torna o assert de "+1" confiável.
3. **O cenário não altera a janela da guarda** — nada de sleep artificial pra "forçar"
   o timing; a determinística vem da ordem (modal de PIN aberto → injeção → PIN).
4. **Um CT novo = 1 linha nova em `TBL_CENARIOS`** — não reutilize o ID de cenário
   removido (o CT03.6 já existiu para "limite negativo" e foi removido no commit
   `1da996d`; este cenário nasceu como CT03.6 e virou CT03.7 justamente por isso).
